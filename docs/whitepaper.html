facecam

Camera → motion → local vision LLM → recording + alert · White paper · October 2026

1. Summary

facecam is a Python security-camera system that runs entirely on the owner's own computer. A camera is watched continuously with cheap motion detection. Only when something moves is a single image sent to a local vision-language model (LLM), which says whether a person is in the picture and how sure it is. If a person is confirmed, the Python program saves a video recording and sends a notification to the owner. No image or video leaves the machine except the alert the owner chooses to receive.

StepWhat happens
1. CameraOpenCV (cv2.VideoCapture) reads frames from the webcam or an IP camera. A small rolling buffer keeps the last few seconds in memory, so the recording can include the moments before motion was noticed.
2. Motion detectionEach frame is shrunk, blurred and compared with a background model (OpenCV background subtraction). If enough pixels change, motion is declared. This step is very cheap, so it runs on every frame and keeps the LLM idle most of the time. A cooldown (for example 5–10 seconds) stops one event from triggering many LLM calls.
3. SnapshotWhen motion starts, the sharpest recent frame is selected and saved as a JPEG, resized to the model's preferred input size to keep inference fast.
4. Local LLMThe image is sent to a vision model running on the same computer (served by Ollama on localhost). The prompt asks for strict JSON only: {"person": true/false, "confidence": 0.0–1.0, "description": "..."}. The reply is the accuracy ratio the system acts on.
5. DecisionPython parses the JSON. If person is true and confidence is at or above a set threshold (default 0.6), the event is confirmed. Malformed or timed-out replies are treated as "no decision" and logged, never as an alert.
6. Record and notifyOn confirmation, Python writes the buffered pre-roll plus live frames to an MP4 (cv2.VideoWriter) until motion has stopped for a few seconds. It then sends a notification (phone push via ntfy or Telegram, or email) containing the snapshot, the model's description and its confidence, and the path of the recording.

3. Choosing the local LLM

The goal is the best person-recognition quality with the fastest response, on ordinary hardware. The recommended setup uses two tiers, both small enough to run on a laptop through Ollama:

RoleModel (suggested)Why
DefaultQwen2.5-VL 3BStrong at following the "reply in JSON" instruction and at describing people in a scene, at a size that stays responsive on CPU or a modest GPU.
Fastest fallbackMoondream 2Around 2B parameters, very quick, suited to weak machines; less reliable on small or partly hidden people.
Higher accuracyQwen2.5-VL 7BBetter on dark or cluttered scenes if a GPU is available; slower.

This ranking is a starting recommendation, not a measured result. The right choice depends on the user's hardware, so the project should include a small benchmark (section 6) that times each model and scores it on the user's own camera images before one is fixed as the default.

4. Why a local LLM instead of a cloud API

ReasonLocal LLMCloud API (e.g. Claude API)
PrivacyImages stay on the owner's machine and are never handed to a third party.Every snapshot is uploaded to the provider's servers.
CostNo per-image fee after the hardware is bought.Billed per image, which adds up quickly on a busy camera.
Response timeNo upload or network round trip; speed depends on the local hardware.Adds upload time and network delay to every check.
AvailabilityWorks with the internet down, when a camera is needed most.Stops working without a connection or during an outage.
ControlThe owner chooses the model, version and settings, and nothing changes unannounced.Model, limits and pricing are set by the provider.

Trade-offs. Small local models are generally less accurate than the largest cloud models, and local speed depends on the computer; this is why the benchmark in section 6 matters. Local also does not mean automatically secure: recordings sit on the owner's disk and need encryption and automatic deletion of old clips. Notification services are still third parties, so the owner can choose text-only alerts and keep snapshots and video on the machine.

5. Design details that make it reliable

  • Confidence is self-reported. A language model does not produce a calibrated probability; the number is its own estimate. It is useful for ranking and thresholding but should be tuned against real events, and treated as a guide rather than a guarantee.
  • False alarms. Pets, shadows and headlights cause motion without a person; the LLM step rejects these, and the threshold sets the balance between missed people and false alerts.
  • Optional face check. The existing facecam modules (YuNet detection, SFace recognition) can run on the confirmed snapshot to tell the owner from a stranger, so the owner is not alerted about themselves.
  • Timeouts. If the LLM is too slow, fall back to the faster model or send an “unverified motion” alert, so no event is silently lost.

6. Proposed code layout

facecam/
  camera.py     read frames, rolling pre-roll buffer
  motion.py     background subtraction, cooldown
  vision.py     send snapshot to local LLM, parse JSON reply
  recorder.py / notify.py   MP4 clips, alerts
  pipeline.py   ties the steps together (main loop)
  cli.py / config.py   commands, thresholds, model, settings

A benchmark command would run each candidate model over a folder of labelled images (person / no person) and report response time and the false-alert and missed-person rates, giving evidence for the model choice and threshold.

7. Privacy, security and limits

  • Local first. Frames, snapshots, recordings and LLM inference all stay on the machine. The only outbound data is the notification the owner configures; an alert can be sent as text only if the owner prefers.
  • Sensitive data. Recordings and face data are personal data. Use an encrypted disk, restrict access, delete old clips automatically, and only film where the law and consent allow.
  • Not a guarantee. A vision model can miss a person or be fooled. Treat facecam as an extra layer, not the only protection for anything valuable. Its accuracy has not yet been benchmarked.

8. Status

The repository currently contains face detection and recognition. The pipeline above is the design for the next stage, built in this order: motion and snapshot, LLM call, recording, notifications, benchmark, optional face check.
